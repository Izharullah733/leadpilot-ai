# Phase 2A Stage 5 — Settings and in-app notifications

Stage 5 moves company configuration, profile preferences, and in-app notifications to Supabase while preserving the existing application workflows. External delivery, AI scoring, file uploads, and integrations remain intentionally deferred.

## Architecture

Reads are server-side and flow through typed repositories in `src/data-access/repositories`, then services in `src/data-access/services`. Mutations use validated server actions and controlled database RPCs. UI components do not issue raw Supabase settings or notification queries, and normal application operations do not use the service-role credential.

Company identity remains in `companies`. Regional preferences, service/source catalogs, versioned scoring rules, and notification defaults are in `company_settings`. Per-membership notification overrides are in `user_notification_preferences`. Profile name, Pakistani mobile number, and timezone remain in `profiles`; Auth owns email. `company_settings_audit` is append-only and records the actor, action, changed field names, and time without retaining secrets or full values.

## Permissions

| Capability | Owner | Admin | Sales manager | Representative |
| --- | --- | --- | --- | --- |
| Read selected-company settings | Yes | Yes | Yes | Yes |
| Update company profile/configuration | Yes | Yes | No | No |
| Update own profile | Yes | Yes | Yes | Yes |
| Update own notification preferences | Yes | Yes | Yes | Yes |
| Read/mark own notifications | Yes | Yes | Yes | Yes |
| Create arbitrary notifications | No | No | No | No |

The selected company is resolved from active database membership. RPCs validate `auth.uid()`, company membership, role, optimistic timestamps, and tenant relationships. Direct browser writes to companies, company settings, profiles, notifications, and audit rows are revoked. Notification RLS is recipient-only. Related lead, follow-up, and appointment foreign keys must belong to the notification company.

## Catalogs and scoring

Services and lead sources are company-specific arrays. Names are trimmed, length-limited, HTML-like input is rejected, and duplicates are compared case-insensitively. Values used by leads cannot be removed; they can be disabled. New-lead and lead-edit forms load only enabled values, while an existing disabled value remains visible on its record. A database trigger rejects forged service/source values.

Scoring rules use JSON version `1` with five integer weights (`budget`, `timeline`, `source`, `completeness`, and `service`), warm/hot PKR thresholds, and high-intent services. Weights must total 100 and the hot threshold must exceed the warm threshold. Stage 5 does not recalculate existing scores and does not add AI scoring; a future recalculation workflow is an explicit later boundary.

## Notification lifecycle

Trusted database triggers create idempotent notifications for lead assignments/reassignments/conversion, follow-up assignment/rescheduling/completion, appointment creation/rescheduling/confirmation/cancellation, and membership changes. Only active same-company recipients are eligible. A stable event key and unique partial index prevent duplicates. Preferences are applied to eligible categories; membership security events cannot be disabled.

The topbar loads a bounded recent list and unread count server-side. It provides an accessible panel, empty state, pending/error feedback, related-record links, mark-one-read, and mark-all-read. Read mutations verify the current authenticated membership and recipient. The UI resynchronizes after tenant switches.

Due/overdue alerts are generated by `process_follow_up_notifications`. It computes each company day using its configured timezone, ignores completed/cancelled/deleted work, excludes inactive members, and uses deterministic event keys. For local development run:

```bash
npm run notifications:process-local
```

The script refuses non-local Supabase URLs, obtains the local service credential only in process memory, and logs counts—not credentials. A future hosted scheduler may invoke the same service-only RPC; no permanent scheduler is installed in this stage.

## Validation and tests

Reset and validate locally with:

```bash
npx supabase db reset
npm run auth:prepare-local
npx supabase test db
npx supabase gen types typescript --local --schema public > src/types/database.ts
npm run lint
npm run build
npm start
npm run qa:e2e
npm audit
```

Database tests cover role restrictions, tenant isolation, controlled privileges, optimistic updates, validation, audit immutability, own-profile writes, recipient-only notification reads, related-record tenant checks, inactive-member exclusion, and due/overdue idempotency. Browser QA covers the settings roles and forms, catalogs, scoring validation, preferences, profile persistence, event notifications, read controls, tenant switching, and 1440/820/430/390 layouts, in addition to the existing authentication and business workflows.

## Deferred limitations

Email, WhatsApp, SMS, push delivery, OpenAI, Facebook Lead Ads, payments, public onboarding, avatar uploads, a full notification archive page, and production cron infrastructure are not implemented. The integrations panel labels these honestly as Coming Soon. Recommended next work is deployment/operational hardening or a separately approved integration stage; external integrations should begin only after production credentials, delivery retry policy, monitoring, and privacy requirements are approved.
